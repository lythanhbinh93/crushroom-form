## Spot-Check: JOIN GID Parsing Edge Case

**Risk identified in spec:** `split_part(pv.variant_id, '/', -1)::bigint` may throw on malformed GID.

### Code Path Analysis
1. **Matview SQL (line 162):** `split_part(pv.variant_id, '/', -1)::bigint = old.line_variant_id`
   - Function: `split_part(string, separator, field_number)`
   - Field `-1` = last field of GID after splitting on `/`
   - Example: `"gid://shopify/ProductVariant/123"` → last field = `"123"` → cast to bigint = 123
   
2. **Malformed GID Scenarios:**
   - Numeric variant ID that's invalid (e.g., > 2^63): Cast throws at matview refresh time
   - GID missing numeric suffix (e.g., `"gid://shopify/ProductVariant/"` or `"gid://shopify/ProductVariant/abc"`): `split_part` returns non-numeric string; cast throws
   - SQL NULL: `split_part(NULL, ...)` returns NULL; `NULL::bigint` returns NULL (not an error)

3. **Test Coverage Gap:**
   - get-variant-breakdown.test.ts tests helper function `gidToNumber` logic (line 67-72 in code) which gracefully returns null on invalid GIDs
   - **However:** SQL matview JOIN does NOT have equivalent graceful handling — cast will throw if encountered
   - **Test coverage:** ⚠️ No test exercises matview-level GID parsing failure (would require ETL integration test)

4. **Risk Level:** 🟡 MEDIUM
   - **Why:** Shopify GID format is stable; invalid GIDs should not exist in schema unless upstream ETL bug
   - **Mitigation:** Matview refresh is run in service_role context with error logging via etl/run-daily.ts
   - **Recommendation:** Add integration test that seeds a variant with malformed GID and asserts matview refresh fails gracefully with error log
