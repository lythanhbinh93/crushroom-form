## P1 — Important (fix in next iteration)

### P1-1. Section-level fallback URLs lack `javascript:` guard
**Files:**
- `sections/dopamiles-home-hero.liquid:28, 33` — `section.settings.cta_primary_url`, `section.settings.cta_secondary_url`
- `sections/dopamiles-home-manifesto.liquid:15` — `section.settings.read_more_url` (always rendered, not fallback)
- `sections/dopamiles-home-manifesto.liquid:61` — `section.settings.cta_url`

Phase 02 correctly applied the URL guard to `blocks/column.liquid` (lines 10-18) — and it is actually **better** than the Phase 01 pattern because it `downcase`s before `contains` (catching `JavaScript:` and `JAVASCRIPT:`). However, the same merchants whose CTAs become blocks via migration still have access to the unguarded `section.settings.*_url` fields in fallback paths.

A merchant pasting `javascript:alert(document.cookie)` into the hero's `cta_primary_url` field gets a live XSS sink on the homepage, regardless of whether they later migrate to blocks. The fallback path (`{%- else -%}`) runs only when `section.blocks.size == 0`, but the manifesto's `read_more_url` (line 15) is in the **always-rendered** section header.

**Fix:** apply the same `downcase + contains` guard from `blocks/column.liquid` to all 4 section-level URL outputs. ~8 lines per section. Could be deferred to Phase 03 (theme-wide URL audit) but should not ship to production.

### P1-2. `blocks/column.liquid` URL guard is stricter than Phase 01's — backport recommended
**File:** `blocks/column.liquid:10-18` vs `blocks/dop-cta.liquid:17-20`

The Phase 02 `column.liquid` guard pattern correctly handles case (`url_lower contains 'javascript:'`). Phase 01's `dop-cta.liquid`, `dop-cta-pair.liquid`, `dop-feature-row.liquid` do **not** downcase before contains — so a merchant typing `JavaScript:alert(1)` bypasses the Phase 01 guard.

Out of strict Phase 02 scope, but flag for backport (Phase 01 maintenance round). Suggested rule for the team going forward: always `downcase` the URL before the scheme-prefix check.

### P1-3. `BlockIdUsage` warning in shop-grid is pre-existing but propagates fragility
**File:** `sections/dopamiles-home-shop-grid.liquid:64` (theme-check confirmed)

```
[warning]: BlockIdUsage
The ID is dynamically generated by Shopify and is subject to change. You
should avoid relying on a literal value of this ID.
64  {%- if block.id == active_tab and block.settings.collection != blank -%}
```

This means URLs like `?tab=<block-id>` are unstable: when a merchant edits/re-orders tab blocks, IDs may rotate, breaking bookmarked URLs and email-campaign deep links. Phase 02 did not introduce this issue (1 warning pre and post migration — confirmed by git stash test), but kept the pattern.

**Robust fix:** use `block.settings.label | handleize` as the tab key instead of `block.id`. Stable across edits. Requires section + tab block changes; can be deferred to Phase 03.

### P2-2. Heading hierarchy skips levels (pre-existing, preserved verbatim)
- `pillar.liquid` emits `<h4>` under a section `<h2>` — skips `<h3>`. WCAG 2.4.6 soft warning.
- `review.liquid` emits `<h5>` (line 27) under a section `<h2>` — skips `<h3>`, `<h4>`. WCAG 2.4.6 soft warning.

Both are 1:1 ports of the pre-migration markup. Don't fix in this PR — collect a11y debt for a dedicated pass. Note: the column block's `<h3>` is correct under the manifesto `<h2>`.

### P2-3. `tab.liquid` is a phantom — file exists to satisfy `@theme`, never rendered
**File:** `blocks/tab.liquid`

The shop-grid section ignores `{% render block %}` for tabs because it needs `request.param.tab` (section scope). The `tab.liquid` file therefore exists only to satisfy Shopify's `@theme` schema requirement. The leading `{%- comment -%}` block does explain this — good. But:
- The phantom file has `aria-selected="false"` hardcoded (no active state) and `class="doh-niche-tab"` without an `active` modifier.
- **Risk:** if a merchant later adds a `tab` block to a *different* section that does `{% render block %}`, they get a broken anchor pointing to `?tab=<id>` on an unrelated template. Low probability (the block name is generic enough to be picked up by accident). Mitigation: rename to a more namespaced type like `niche-tab` so it's less attractive to other sections. Deferred — not a Phase 02 regression.

### P2-4. Hero `stat` block adds new `caption` setting beyond pre-migration markup
**File:** `blocks/stat.liquid` lines 36-39 + `pre-migration sections/dopamiles-home-hero.liquid`

Pre-migration hero rendered `<div class="m"><b>{{stat_X_value}}</b><span>{{stat_X_label}}</span></div>` — no third element. The new `stat.liquid` adds an optional `<small>{{caption}}</small>`. This is markup expansion, not parity. Default for `caption` is empty, so blank-by-default — no live regression. Cosmetic only; flagged for awareness.

### P2-5. `column.liquid` outputs `href="{{ safe_url }}"` without explicit `| escape`
**File:** `blocks/column.liquid:31`

Liquid auto-escapes attribute-context output, so this is safe in practice. But Phase 01 `dop-cta.liquid` uses the same pattern (`href="{{ safe_url }}"`), so this is consistent — flag only that explicit `| escape` would be defensive and future-proof against Liquid-mode changes. Same nit as Phase 01.

### P2-6. `phrase.liquid` outer wrapper is a `<span>` with `<i>` sibling — unusual
**File:** `blocks/phrase.liquid:7-8`

```liquid
<span {{ block.shopify_attributes }}>{{ block.settings.phrase | escape }}</span>
<i aria-hidden="true">✦</i>
```

Two top-level elements. `block.shopify_attributes` is only on the `<span>` — Theme Editor click-to-select will highlight only the text span, not the `✦` separator. This is fine for the marquee use case (the separator is decorative) but technically the entire block visually includes both elements. Cosmetic.
